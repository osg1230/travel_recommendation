# 여행 조건 입력 구현 기준

기준일: 2026-09-11

## 기준 문서와 이번 범위

- 요구분석서: `docs/requirements/창프2_요구분석서 3.0_관리자범위축소_최종본.docx`의 SFR-02-01~04, UC-06.
- DB: `docs/database/DB_테이블_정의서.md`의 keyword_categories, keywords, recommendation_requests.
- UI-08의 입력·서버 검증과 UI-09의 입력 내용 확인·수정 복귀를 구현한다. 자연어 분석 결과 확인과 추천 요청 확정은 AI 연동 단계에서 완성한다.
- 회원·비회원·관리자가 모두 입력할 수 있다. POST에는 CSRF 토큰이 필요하다.

## 입력과 검증

| 항목 | 처리 기준 |
| --- | --- |
| 입력 방법 | TEXT / KEYWORD만 허용하고 선택한 방법의 값만 임시 보관 |
| 자연어 | 앞뒤 공백 제거 후 1~2,000자. 원문만 확인하며 분석 완료로 표시하지 않음 |
| 지역·계절·동행자·이동수단 | 화면 선택지와 서버 허용 목록을 함께 관리, 미선택은 빈 값 |
| 여행 취향 | 복수 선택, 허용 목록 검증 후 중복 제거, 미선택은 빈 목록 |
| 날짜 | 둘 다 미입력 또는 둘 다 입력. 실제 날짜이며 마지막 날은 출발일 이상 |
| 여행 일수 | 미입력 허용. 입력하면 1~32,767 정수(SMALLINT 범위). 날짜가 있으면 양 끝 날짜를 포함한 일수로 계산하고 직접 입력한 일수와 일치 여부 확인 |
| 예산 | 미입력 허용. 전체 인원의 원화 총예산 상한, 0 이상 DECIMAL(12,2) 범위. 지수·음수·쉼표·소수 셋째 자리 거부 |

날짜·기간·예산 등 미정 조건은 입력 단계에서 강제하지 않고 확인 화면에 ‘상관없음’으로 표시한다. 추천·일정 생성에 필요한 조건의 보완은 이후 분석·확정 단계에서 처리한다. 날짜의 과거 여부와 계절 불일치에 대한 추가 제한은 요구사항에 없어 임의로 적용하지 않는다.

## 임시 보관과 화면

- GET `/travel/conditions`: 입력 화면. 홈에서 진입한다.
- POST `/travel/conditions`: 검증 성공 시 세션에 현재 입력 한 건을 저장하고 확인 화면으로 리다이렉트한다. 오류가 있으면 입력값과 오류를 같은 화면에 표시하며 기존 유효한 임시 입력은 유지한다.
- GET `/travel/conditions/check`: 입력 원문 또는 선택 조건을 확인한다. 임시 입력이 없으면 입력 화면으로 이동한다.
- 수정 링크로 돌아오면 입력값이 유지된다. 다른 세션에는 노출되지 않으며 로그아웃·세션 만료 시 사라진다. 영구 저장·추천 이력으로 취급하지 않는다.
- 문장은 Thymeleaf의 이스케이프 출력을 사용한다. 로그·URL에 원문을 추가하지 않는다.
- 입력 방법 전환은 라디오 선택으로 제공하고, 키워드 항목은 지역·기간·취향·예산/이동수단 링크로 이동한다. JavaScript가 없으면 두 입력 영역을 모두 표시하고 선택한 방법만 처리한다.

## 다음 단계

2026-09-11 후속 작업에서 SQL Server 프로필의 선택지를 키워드 DB에 연결했다. 카테고리와 키워드가 모두 활성인 항목만 표시하고, 제출한 ID가 해당 카테고리에 속하는지 매 요청 검증한다. 선택 당시 ID·카테고리 코드·이름·JSON 값을 세션에 보관하며 확인 화면은 이 이름을 표시한다. 기본 프로필만 예시 목록을 사용한다. DB 오류는 재시도 안내, 빈 목록은 준비 중 안내를 표시한다. 관리자 키워드 관리 화면은 추가하지 않았다.

자연어 분석, 분석 조건의 보완·확정, AI 작업 생성, 요청 이력 저장, 실제 추천 결과는 다음 단계다. 추천 요청을 DB에 저장하거나 외부 API를 호출하지 않는다.
