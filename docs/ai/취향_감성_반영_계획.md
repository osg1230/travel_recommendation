# 취향·감성 반영 계획

작성일: 2026-11-16 | 상태: 1~3단계 구현(하루 흐름은 감성적인의 마무리만), 4단계(재생성 빠른 버튼) 미정 | 브랜치: `feature/place-value-score`

## 1. 배경

지금 일정은 거리·이동시간·하루 장소 수·식사 시간 같은 규칙으로 만든다. 조건이 같으면 누구에게나 비슷한 일정이 나오고, 여행을 가는 이유나 좋아하는 분위기가 일정에 잘 드러나지 않는다.

2026-11-13 [실사용 질문 일정 생성](../quality/2026-11-13_실사용_질문_일정생성.md)에서도 미충족 0인데 질문의 핵심(카페·밤 놀거리·감성 숙소)이 빠진 일정이 6개 중 4개였고, '많이 걷지 않게'·'조용히 쉬기'는 여유 일정으로 인식되지 않았다.

## 2. 사용자 결정 (2026-11-16 선택지 응답)

| 질문 | 고른 답 |
| --- | --- |
| 아쉬운 점 | 취향 표현이 부족함, 입력이 결과에 안 보임, 일정 흐름이 딱딱함 |
| 감성의 의미 | 장소의 분위기, 하루의 이야기, 여행 속도와 여유 |
| 입력 방법 | 문장으로 적은 사람에게 따로 다시 묻는 것은 사용성이 나쁨. 방법은 추천을 받음 |
| 결과에서 느끼는 방식 | 장소 구성 자체가 달라짐, 머무는 시간이 달라짐 (설명 문구보다 실제 구성) |

## 3. 새로 다룰 조건 두 가지

| 조건 | 선택지(안) | 선택 방식 | 비고 |
| --- | --- | --- | --- |
| 여행 분위기 | 한적한, 활기찬, 감성적인 | 여러 개, 선택 입력 | 고르지 않으면 지금과 같다 |
| 여행 속도 | 느긋하게, 보통, 알차게 | 하나, 선택 입력 | 고르지 않으면 '보통' |

"하루의 이야기"는 따로 입력받지 않고, 분위기와 속도에 따라 하루 배치 순서를 바꾸는 것으로 반영한다(5.3).

## 4. 입력: 더 묻지 않고, 읽은 것을 보여 주고 고치게 한다

### 4.1 문장으로 적기

- 자연어 조건 분석([자연어 조건 분석](자연어_조건_분석.md))의 AI 응답에 `mood`, `pace`를 더한다. 문장에 근거가 없으면 비워 두게 한다. GPT 호출 수는 늘지 않는다.
- 서버는 허용된 선택지 값만 받고 나머지는 버린다(AGENTS.md 9절).
- 조건 확인 화면(`travel/condition-review.html`)에 두 항목을 칩으로 보여 주고, AI가 읽은 값을 미리 선택해 둔다. 안내 문구 예: "적어 주신 문장에서 읽었어요. 다르면 바꿔 주세요." 사용자는 틀렸을 때만 누른다.
- 지금의 낱말 찾기(`RelaxedPace`)는 AI가 속도를 못 읽었을 때의 보조로 남기고, '많이 걷지 않게'·'조용히 쉬기' 같은 말을 더한다.

### 4.2 조건 고르기

- 조건 입력 화면(`travel/conditions.html`)의 "계절·동행자·취향" 카드 아래에 분위기·속도 한 줄을 선택 입력으로 둔다.

### 4.3 저장

- `keyword_categories`에 `MOOD`, `PACE` 카테고리를, `keywords`에 3.의 선택지를 새 초기 데이터 SQL로 추가한다. 고른 값은 지금처럼 추천 요청의 `conditions_json.selected_keywords`에 들어간다. **테이블·컬럼 변경은 없다.**
- 영향: DB 정의서 3.2의 "카테고리는 추가하지 않는다(질문 5개 고정)"를 질문 7개로 고치고, 관리자 키워드 관리에서 두 카테고리는 이름 변경·추가를 막는 목록(AGENTS.md 6절)에 넣는다. 추천 규칙이 이름을 그대로 쓰기 때문이다.
- 대안: 분위기를 기존 THEME(여행 취향) 키워드로 넣으면 카테고리를 늘리지 않아도 된다. 다만 '바다·자연' 같은 장소 종류와 '한적한' 같은 느낌이 한 줄에 섞여 고르기 헷갈릴 수 있다. 속도는 하나만 고르는 값이라 THEME에 넣기 어렵다. → 6. 결정 필요.

## 5. 결과 반영: 장소 구성과 머무는 시간이 달라지게

### 5.1 여행 속도 → 하루 장소 수와 체류 시간

`RelaxedPace`를 속도 세 단계로 넓힌다.

| 속도 | 하루 관광지 | 체류 시간 | 저녁 관광 | 남는 시간 |
| --- | --- | --- | --- | --- |
| 느긋하게 | 3곳 | 종류별 기본보다 길게(예: 1.3배, 해변 120분은 유지) | 넣지 않음 | 채우지 않음 |
| 보통 | 지금과 같음(4곳까지) | 지금과 같음 | 지금과 같음 | 지금과 같음 |
| 알차게 | 4곳 이상(검증 상한 안) | 지금과 같음 | 넣음 | 관광지로 채움 |

사용자가 하루 방문 수를 직접 정했으면 그 값을 우선한다(지금 규칙과 같다).

### 5.2 여행 분위기 → 고르는 장소의 종류

가치 점수(`PlaceValueScore`)에 분위기 기준을 더한다. 2026-11-09 내 기록 취향 점수와 같은 방식(가점 후 100점에서 자름)이다.

| 분위기 | 점수를 올리는 곳(`ThemePlaces` 종류·이름 기준) | 점수를 낮추는 곳 |
| --- | --- | --- |
| 한적한 | 자연·휴식(수목원, 둘레길, 호수, 휴양림) | 랜드마크 점수 비중을 줄여 유명 관광지 쏠림을 낮춤 |
| 활기찬 | 시장, 거리, 테마파크, 야경 명소 | - |
| 감성적인 | 카페거리, 미술관·전시, 정원, 한옥, 전망대·해변 | - |

- 한계: 외부 데이터로 실제 붐비는 정도는 알 수 없다. 장소 종류로 추정하므로 화면에 "한적한 곳"이라고 단정하지 않고 "조용히 둘러보기 좋은 종류예요"처럼 쓴다(AGENTS.md 9절).
- GPT 후보 요청에도 분위기를 한 줄 넘겨 후보 단계부터 맞는 곳이 나오게 한다(요청 수는 그대로).

### 5.3 하루 흐름

- 하루 순서를 "가볍게 시작 → 오후에 중심 장소 → 여유 있게 마무리"로 배치한다. 체류가 긴 곳을 오후 앞쪽에 둔다.
- 감성적인: 그날 마지막 관광을 해변·전망대처럼 해질녘에 어울리는 곳으로 둔다(동선이 크게 늘지 않을 때만).
- 느긋하게: 숙소에 일찍 들어가고 저녁은 숙소 근처에서 먹는다(11-11 동작 유지).

## 6. 결정 (2026-11-16 사용자, 권장안대로)

1. 분위기 선택지는 3.의 안(한적한·활기찬·감성적인), 속도는 느긋하게·보통·알차게.
2. 새 카테고리 `MOOD`·`PACE`를 추가한다.
3. '느긋하게' 체류 배율 1.3배. '알차게' 하루 상한은 2단계에서 검증 상한 안에서 정한다.
4. 재생성 빠른 버튼은 선택 단계로 두고 2·3단계 뒤에 다시 정한다.

## 7.1 1단계 구현 (2026-11-16)

- 데이터: `019_seed_mood_pace_keywords.sql`(행만 추가), DB 정의서 3.3.
- 입력: `TravelConditionForm.moods`·`pace`, `TravelConditionOptions`에 `moods`→MOOD·`pace`→PACE, 조건 입력·확인·확인표·확정 화면에 두 항목. 입력 칸 허용 목록(`@InitBinder`)에도 넣었다.
- AI: 조건 분석 응답에 `moods`(분위기 선택지 값 배열)·`pace`(속도 선택지 값 하나 또는 null)를 더했다. 응답 형식은 strict 스키마와 활성 선택지 enum으로 묶고, 서버는 목록에 없는 값이면 그 칸만 비우고 안내한다. GPT 호출 수는 그대로다.
- 관리자: MOOD·PACE는 이름 변경·추가를 막는다(`AdminKeywordService.FIXED_CATEGORIES`).
- 아직 일정에는 반영하지 않는다(2·3단계). 지금은 고른 값이 조건과 확인 화면에 보이고 추천 요청에 저장된다.

## 7.2 2단계 구현 (2026-11-16)

- `RelaxedPace`가 고른 속도(PACE 키워드 이름)를 먼저 본다. 고르지 않았을 때만 문장 낱말로 여유 일정을 찾고, 낱말에 '많이 걷지 않게'·'푹 쉬'를 더했다.
- 느긋하게: 하루 3곳(선호), 저녁 관광 없음(11-11 동작), 체류시간 1.3배(10분 단위, 최대 240분), 바다 취향이면 해변 120분 이상.
- 보통: 지금까지와 같다. 문장에 "여유롭게"가 있어도 '보통'을 고르면 여유 일정이 아니다.
- 알차게: 남는 시간을 예비 관광지로 채울 때 하루 상한 4곳 → 5곳(`PACKED_DAILY_CAP`). 짧은 곳이 많으면 한 곳 더 넣는 기존 규칙도 이 상한 기준이다. 조건 확인표의 하루 방문 수에 이유를 적는다. 실제 비교에서 상한만으로는 보통과 같아, 체류시간 0.8배(10분 단위, 최소 30분, 한라산 탐방로 제외)를 더했다(같은 날 사용자 결정).
- DB·작업 JSON 변경 없음. GPT 요청은 그대로다.
- 확인: `RelaxedPaceTests` 새 2개·수정 1개, `ItineraryGeneratorTests.packedPaceLetsSpareFillReachFiveVisits`. DB 없이 도는 전체 795개 실패 0.
- 실제 비교([여행 속도별 일정 비교](../quality/2026-11-16_여행속도별_일정비교.md)): 느긋하게는 의도대로 달라졌다. 알차게는 기본 시간(09:00~18:00)에서 하루 시간이 상한보다 먼저 차서 보통과 거의 같았다. 체류 0.8배를 더한 뒤 다시 만들어 1일차 낮 6곳·체류 50~70분으로 보통과 달라진 것을 확인했다. 2일차는 4곳·15:07에 끝났고 이유는 확인하지 않았다.

## 7.3 3단계 구현 1: 분위기 점수 (2026-11-16)

- 새 `MoodPlaces`: 분위기별로 분류·장소 이름의 낱말로 어울리는 종류를 정한다. 한적한 = 수목원·휴양림·숲·둘레길·호수·계곡·정원·사찰 등, 활기찬 = 시장·거리·테마파크·광장·해수욕장 등, 감성적인 = 카페·미술관·전시·정원·한옥·전망대·등대·해변 등.
- `PlaceValueScore`에 분위기 기준(10점)을 더했다. 내 기록처럼 더한 뒤 100점에서 자른다. 한적한을 고르면 대표 관광지 가중치를 25 → 12.5로 줄인다. 일정 생성은 이 점수로 다음 장소를 고르므로 장소 구성이 바뀐다.
- GPT 장소 고르기 요청에 MOOD·PACE를 넘기고, 분위기에 맞는 곳을 앞에 두라고 지시했다(PACE는 순서에 쓰지 않음). 호출 수는 그대로다.
- 일정 항목의 고른 이유에 "고른 분위기(감성적인)와 어울리는 종류"를 적는다. 실제 분위기를 확인한 것이 아니라서 단정하지 않는다.
- DB·작업 JSON 변경 없음. 테스트: 새 `MoodPlacesTests` 2개, `PlaceValueScoreTests.moodAddsTenPointsAndQuietHalvesTheLandmarkWeight`. DB 없이 도는 전체 798개 실패 0.
- 실제 비교([여행 분위기별 일정 비교](../quality/2026-11-16_여행분위기별_일정비교.md)): 점수와 고른 이유는 동작하지만 장소 구성은 크게 바뀌지 않았다. 후보를 바다 취향·대표 관광지로만 찾아 한적한 종류가 후보에 거의 없고(0~1곳), 해변이 활기찬·감성적인 둘 다에 걸린다.
- 분위기 검색어(같은 날 사용자 결정): `MoodPlaces.searchWords`로 장소 목록을 모을 때 카카오에서 더 찾고(`PlaceDiscoveryService`, 검색어당 3곳), 분위기 검색 종류의 관광지 중 검색 순서 앞 3곳을 일정 후보에서 취향 장소보다 앞에 둔다(`PlaceCandidateService`). 해수욕장·해변은 분위기 낱말에서 뺐다. 후보에는 들어가지만 GPT 본편 순서에서 밀려 대부분 예비·저녁 후보로 남는다. DB·작업 JSON 변경 없음. 새 테스트 2개, 전체 800개 실패 0. SQL Server 후보 정렬 통합 테스트는 실행하지 않았다.
- 하루 1곳 보장(같은 날 사용자 결정): `MoodPlaces.moodFirst`가 낮 관광지를 고르기 직전에 분위기 장소를 일수만큼 앞으로 당긴다(`PlacePickService`, `ItineraryJobService`). 실제 실행에서 수목원·테마파크가 본편에 들어갔다. 활기찬·감성적인 1일차 오후가 빈 문제(예비 관광지 0~1곳)가 보였고 원인은 확인하지 않았다. 새 테스트 1개, 전체 801개 실패 0.
- 1일차 오후가 빈 원인: MOOD를 넘긴 뒤 AI가 분위기와 맞지 않는 대표 관광지까지 skip에 넣어 예비가 0~1곳만 남았다. GPT 지시에 'MOOD·PACE는 skip에 쓰지 않음'을 넣고, 예비가 4곳보다 적으면 skip한 곳을 AI 순서대로 채우는 안전장치(`MIN_RESERVE`)를 더했다. 다시 실행한 활기찬·감성적인은 skip 1~2곳, 1일차 낮 5곳이었다. 전체 802개 실패 0.


## 7.4 3단계 구현 2: 하루 흐름 (2026-11-16)

- 감성적인을 고르면 그날 관광지를 정한 뒤, 바다·전망 장소(해수욕장·해변·해안·등대·전망대·스카이워크)를 하루 마지막으로 옮겨 다시 넣어 본다(`MoodPlaces.sceneryLast`, `ItineraryGenerator`). 이미 마지막이 풍경이면 그대로 두고, 직선거리가 5km(`ENDING_EXTRA_KM`)보다 늘거나 시간·운영시간이 맞지 않으면 원래 순서를 쓴다. 옮긴 곳의 고른 이유에 "하루를 바다·전망 풍경으로 마무리하도록 마지막에 둠"을 적는다. 기존 '더 짧은 순서로 다시 넣기'와 같은 방식이다.
- 5.3의 '가볍게 시작 → 중심 장소 → 여유 있게 마무리' 전체 배치는 넣지 않았다. 지금은 그날 중심 장소를 첫 관광지로 넣는 규칙이 있어 서로 부딪힌다. 느긋하게의 일찍 숙소 들어가기는 2단계 동작 그대로다.
- 확인: 새 테스트 2개(`MoodPlacesTests.sceneryLast…`, `ItineraryGeneratorTests.emotionalTripEndsTheDayAtTheScenery`), 전체 804개 실패 0. 웹 서버에서 감성적인 강릉 일정을 한 번 만들었는데 두 날 모두 이미 해변으로 끝나 규칙이 쓰이지 않았다(바닷가 여행지는 대개 그렇다). 실제 적용은 내륙 여행지 등에서 확인이 필요하다.
- 내륙 확인(같은 날, 충북·자연·감성적인·자차·2일 → 단양, 11-26 출발, 추천 1회·일정 1회): 1일차 온달관광지 → 보발재전망대 → 고수동굴 → 도담삼봉 → 숙소 → 저녁 관광 양방산전망대, 2일차 만천하스카이워크 → 단양강잔도 → 수양개빛터널 → 소선암자연휴양림 → 사인암. 두 날 모두 전망 장소가 있었지만 마지막으로 옮기지 않았다. DB 좌표로 계산하면 옮길 때 하루 직선거리가 1일차 19.6 → 39.8km, 2일차 13.2 → 22.0km로 5km 기준을 넘어, 규칙대로 원래 순서를 쓴 것이다. 1일차는 저녁 관광(양방산전망대, AI 밤 명소)이 풍경으로 하루를 마쳤다.
- 정리: 하루 마무리 규칙은 동작하지만 기준이 보수적이라, 전망 장소가 하루 동선의 한쪽 끝에 있는 단양에서는 적용되지 않았다. 실제로 쓰인 경우는 아직 없다(테스트로만 확인).
- 남은 것: 하루 마무리를 더 자주 쓰려면 기준(5km)을 늘리거나 다음 장소를 고를 때부터 풍경 장소를 뒤로 미루는 방식이 필요하다(결정 필요). 4단계 재생성 빠른 버튼(선택).
