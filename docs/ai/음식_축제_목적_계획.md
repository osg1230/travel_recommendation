# 음식·축제 목적 반영 계획

작성일: 2026-11-16 | 상태: 계획(코드 변경 없음) | 브랜치: `feature/place-value-score`

## 1. 배경

"김밥 축제 ㄱㄱ"라고 입력했더니 여행지를 찾지 못했다(같은 날 사용자 테스트). 김천 김밥축제는 실제로 있다(2025-10-25~26, 직지문화공원·사명대사공원 일대, 2회째, 언론 보도 기준). 사용자 의견: 축제가 끝났더라도 그 음식의 맛집을 탐방하는 일정으로 바뀌었으면 좋겠다.

## 2. 지금 동작과 원인 (작업 요청 JSON `F9CEDEC5…`로 확인)

| 단계 | 결과 | 원인 |
| --- | --- | --- |
| 조건 분석 | 목적 "김밥 축제 관람", 지역 없음 | 정상 |
| 지역 제안(`RegionSuggestionService`) | AI가 **경상북도 김천시** 제안 → NONE | 근거 확인에 쓰는 관광공사 분류(`WishCategories`)에 **축제·음식이 없다**. AI가 '전통문화체험'(EX010100)을 골랐고 김천에 그 장소가 없어 빠졌다. |
| 목적 시설 검색(`PurposePlaceService`) | 검색어 "축제" → NONE | 검색어를 만들며 **"김밥"이 빠졌다**. 이 검색은 관광지·문화시설만, 서비스 여행지 안에서만 찾는다. |
| 일정 식사 | (해당 없음) | 식사는 동선·인기 음식점·지역 대표 음식으로만 고르고, 사용자가 원한 음식은 보지 않는다. |

## 3. 목표

- 음식이나 음식 축제를 말하면, 그 음식으로 알려진 지역을 외부 데이터로 확인해 여행지로 추천한다.
- 여행 기간에 축제가 열리면 축제 장소를 일정에 넣는다(기존 축제 기능). 열리지 않거나 확인되지 않으면 **그 음식 맛집 탐방**으로 바꾸고, 바꾼 이유를 화면에 알린다.
- 일정의 식사에 그 음식 음식점을 우선한다.

## 4. 단계

### 1단계: 목적에서 음식 이름 남기기

- `OpenAiPurposeClient` 응답에 `food`(예: "김밥", 없으면 빈 문자열)와 `festival`(축제를 말했는지)을 더한다. 검색어를 만들 때 "김밥"처럼 대상이 되는 말을 빼지 말라는 지시를 넣는다.
- 서버 검증: 음식 이름은 한글 1~10자만 받는다(AGENTS.md 9절).
- 저장: 작업 JSON의 `PurposeSearch`에 `food`·`festival` 필드 추가(테이블 변경 없음, DB 정의서 작업 JSON 설명 갱신).

### 2단계: 음식으로 지역 확인

- `RegionSuggestionService.check`에서 관광공사 분류로 근거가 없더라도, `food`가 있으면 카카오에서 "○○시 김밥" 음식점을 검색해 그 시·군 주소의 음식점이 N곳(안: 3곳) 이상이면 근거로 본다.
- 서비스 여행지에 없던 시·군이면 지금 규칙(2026-10-30 결정)대로 여행지로 추가한다. 설명에는 "김밥 음식점 ○곳 확인(카카오)"처럼 근거를 적는다.

### 3단계: 축제 확인과 맛집 탐방 전환

- 관광공사 행사 정보(축제)에서 그 시·군과 음식 이름이 들어간 행사를 찾는다. 여행 기간과 겹치면 기존 축제 안내·축제 장소 흐름을 쓴다.
- 겹치지 않거나 찾지 못하면 여행 목적을 "김밥 맛집 탐방"으로 바꾸고 추천·일정 화면에 안내한다. 예: "여행 기간에 열리는 김밥 축제를 찾지 못해 김밥 맛집 위주로 일정을 짰어요." 최근 개최 기간을 확인했으면 함께 보여 준다.
- 축제 일정은 바뀔 수 있으므로 확인한 날짜와 출처를 함께 적는다.

### 4단계: 음식점 후보와 식사 고르기

- 장소 목록을 모을 때(`PlaceDiscoveryService`) "○○ 김밥" 음식점을 카카오에서 더 찾고, 일정 후보(`PlaceCandidateService`, 음식점 8곳)에서 앞에 둔다(분위기 장소를 앞에 두는 방식과 같다).
- 식사 고르기(`ItineraryGenerator`)에서 상호·분류에 고른 음식이 들어간 음식점을 지역 대표 음식보다 먼저 고른다. 하루 최소 한 끼, 여행 전체에서 같은 식당은 다시 고르지 않는다. 고른 이유에 "고른 음식(김밥) 음식점"을 적는다. 메뉴를 확인한 것은 아니라는 안내는 지금 대표 음식 안내와 같게 둔다.

## 5. 결정 필요

1. 음식 근거로 볼 음식점 수(안: 3곳 이상).
2. 축제를 볼 기간: 여행 기간만(안) vs 여행 기간 앞뒤 며칠까지.
3. 고른 음식 식사 수: 하루 한 끼(안) vs 가능한 모든 끼니.
4. 음식만 말한 경우(예: "돼지국밥 먹으러 가고 싶어")도 같은 흐름으로 처리할지(안: 처리).

## 6. 확인 방법

- 단위 테스트: 음식 이름 검증, 음식 근거로 지역 확인, 축제 없음 → 맛집 탐방 전환, 식사에서 고른 음식 우선.
- 실제 확인: "김밥 축제 ㄱㄱ", "부산 돼지국밥 먹으러 가고 싶어" 같은 문장으로 추천·일정을 만든다. OpenAI·카카오·관광공사 호출이 생기므로 실행 전에 확인을 받는다.

## 7. 범위

요구분석서의 "자연어 또는 조건을 통한 여행 조건 입력", "AI 기반 일정 추천" 안이다. 축제·음식 정보는 외부(관광공사·카카오) 데이터로 확인하고 AI는 해석만 돕는다. 관리자 장소 관리 화면은 만들지 않는다.
