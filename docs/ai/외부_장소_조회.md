# 카카오 외부 장소 조회

2026-09-20 구현 기준. 기존 001~007 SQL과 `KAKAO_REST_API_KEY`를 사용하며 추가 스키마 변경은 없다. 최신 Jar로 서버를 재시작한다.

## 사용 방법

추천 지역 선택 → 장소 목록 → **카카오에서 장소 더 찾아보기** → 목록 확인 → **하루 시간을 정하고 일정 초안 만들기** 순서다. 강릉·부산·경주를 지원한다. GPT 추가 호출은 없으며 카카오 API 사용량이 발생한다.

관광지(AT4)·음식점(FD6)·숙소(AD5)를 키워드 검색으로 각각 한 번 조회한다. 유형별 첫 페이지 15개 중 검사를 통과한 관광지 최대 8곳·음식점 5곳·숙소 3곳을 반영한다. 전체 지역 검색이나 취향별 추천 순위가 아니다. 조회 중 버튼과 안내를 바꾸고 실패 시 기존 데이터를 유지한다. 같은 세션의 마지막 성공 요청과 동일한 지역/추천을 60초 안에 재요청하면 추가 호출하지 않는다. 전역 사용량 제한은 아니다.

## 검증과 저장

- 서버가 추천 소유권·만료·지역을 먼저 확인한다. 응답의 장소 ID·유형·지역 주소·국내 좌표·카카오 상세 URL을 검사하고 잘못된 행과 중복 ID를 제외한다.
- 세 종류의 외부 호출을 모두 마친 뒤 짧은 트랜잭션에서 지역을 잠그고 권한·만료를 재검사한다. 일부 API 실패 시 수집분을 부분 저장하지 않는다.
- 기존 `places`에 `source_provider=KAKAO`와 외부 ID로 등록/갱신한다. 기존 SYSTEM 행과 비활성 행을 덮어쓰거나 되살리지 않는다. 안내 개수는 등록 및 갱신한 수이며 순수 신규 개수는 아니다.
- 카카오 후보는 확인 후 24시간 이내만 목록에 포함한다. 오래된 행을 삭제하거나 자동 재조회하지 않으므로 버튼으로 다시 조회해야 한다.
- 같은 유형·정규화한 건물 주소의 중복은 카카오 후보를 우선해 하나만 표시한다. 보수적인 중복 제거로 같은 건물의 서로 다른 업체도 숨겨질 수 있다. 표시 상한은 관광지 16·음식점 8·숙소 5곳이다.

## 일정 연결과 한계

카카오 후보의 검증된 좌표를 일정에 사용하고 기존 SYSTEM 후보는 주소를 조회한다. 충분한 관광지가 있으면 1~7일을 지원한다. 날짜 수×2, 전체 최대 8곳을 후보 순서로 선택하며 입력 화면에서 선택된 관광지 이름을 보여준다. 날짜 수보다 관광지가 적으면 생성하지 않는다. 카카오 우선·이름순 선택이므로 취향·예산 최적 선택은 아니다.

선택된 관광지를 근거리 우선으로 배치하고, 식당은 직전 관광지에서 직선거리상 가까운 후보를 선택한다. 식당은 날짜별로 반복될 수 있고 숙소는 첫 후보를 사용한다. 실제 이동시간과 시간 충돌 검사는 기존 일정 생성기를 따른다. 전역 최단 경로를 보장하지 않는다.

[카카오 공식 REST API 문서](https://developers.kakao.com/docs/ko/kakaomap/rest-api)의 장소 검색 응답에는 영업시간·휴무일이 없다. 따라서 이 조회로 영업 여부·가격·예약 가능성까지 검증했다고 표시하지 않는다. 운영정보 확보·AI 세부 일정 보조·내 일정 저장은 다음 단계다.

## 확인 결과

- Java 21 / SQL Server 전체 `verify`: 127개 중 122개 통과, 선택형 실제 API 5개 건너뜀, 실패·오류 0. Jar 빌드 성공.
- 별도 클라이언트 검증 9개 통과(응답 단위 테스트 8개, 실제 검색 테스트 1개). 실제 검색 9회에서 세 지역 각각 관광지 8·음식점 5·숙소 3곳을 확인했다. 실제 결과를 DB에 저장한 검증은 아니다.
- DB 통합 테스트에서 반복 저장·기존 데이터 유지·24시간 만료·비활성 유지·주소 중복·권한/CSRF·중복 제출·3일 일정 생성과 완료를 검증했다. 지도 응답은 mock이며 DB 변경은 롤백했다.
- MockMvc 렌더링 결과를 임시 정적 서버로 기본 및 390px 너비에서 확인했다. 모바일 콘텐츠 너비/스크롤 너비 모두 375px로 가로 넘침이 없었다. 실제 브라우저의 추천부터 외부 조회/생성까지 전체 제출 흐름은 미수행이다.
