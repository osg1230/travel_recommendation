## 2. 확정한 범위와 정책

### 관리자와 키워드

관리자 업무는 SFR-15-01~03의 회원 목록·상세 조회와 정상(ACTIVE) ↔ 이용 제한(RESTRICTED) 상태 변경으로 제한한다. 관리자에 의한 회원 탈퇴·삭제와 본인 이용 제한은 허용하지 않는다. 관리자는 일반 회원 권한으로 자신의 여행 기능을 이용할 수 있다.

원본 SFR-12-01 및 UC-12의 관리자 키워드 관리, QUR-06의 관리자 화면을 통한 키워드 변경 요구는 적용 제외한다. 관리자 여행지·관광지·숙소·음식점 CRUD와 별도 R3 운영 조회 화면도 제공하지 않는다. 원본의 개발 범위·우선순위·역할·시나리오에서 같은 관리자 기능을 언급한 부분에 동일하게 적용한다.

DAR-07의 키워드 데이터와 사용자 조건 선택 기능은 유지한다. keyword_categories·keywords는 시스템 초기 데이터와 검토한 배포 SQL로 관리하며 관리자 CRUD 화면·API를 만들지 않는다. 기존 테이블·데이터는 삭제하지 않는다. UI-17은 과거 이미지 식별용 제외 번호로 남기고 다른 화면 번호를 당기지 않는다.

### 지역 추천 후보 개수

SFR-03-04·UC-06 및 추천 판정 규칙의 일반 목표는 3~5개이다. 단, 지정 지역과 R1 지원 지역(강릉·부산·경주)을 우선한다. 현재 적용은 실제 조회된 후보 1~5개이며 특정 지원 지역 지정 시 1개, 지역 미지정 시 활성 초기 3개를 비교한다. 비활성·출처 오류 등으로 유효 후보가 줄면 유효한 후보만 사용하고 0개이면 실패 안내한다. 개수를 맞추려고 조건 밖 지역이나 확인하지 않은 후보를 추가하지 않는다.

현재 추천은 조회 후보를 각각 한 번씩 반환하며 입력·결과 ID 집합과 개수를 서버에서 검증한다. 이것은 지역 추천 규칙이고, 상세 일정에 포함할 개별 장소 수를 1~5개로 제한하는 규칙은 아니다.

### 회원과 사용자 데이터

회원가입·로그인은 이메일 대신 login_id를 사용한다. 아이디와 닉네임은 앞뒤 공백 제거 후 같은 DB collation으로 중복 확인한다. ACTIVE·RESTRICTED 회원의 닉네임은 중복을 금지하고 WITHDRAWN 회원은 필터 UNIQUE 대상에서 제외한다. 이 정책은 기존 DB 정의서와 001 SQL에 반영되어 있으며 새 스키마 변경이 아니다.

즐겨찾기 대상은 여행지·관광지·숙소이며 음식점과 일정 자체는 제외한다(SFR-09-01~03, DAR-14). 장소 평가는 기존 R2의 별점 1~5점과 사전 정의 태그 최대 3개로 제한하고 후기 게시판을 추가하지 않는다. 가상 예약·결제는 R3 선택사항이며 실제 예약·결제는 제외한다.

## 3. 일정 배치 기준

SFR-04-04·UC-07 및 3.1의 일정 배치 전략을 다음 순서로 적용한다. 현재 지역 추천 기능과 구분되는 후속 구현이다.

1. 선택한 지역의 실제 관광지·숙소·음식점 후보와 확인 가능한 좌표·테마·운영시간 등을 조회한다.
2. 서버가 사용자 조건 적합도를 점수화하여 후보를 선정하고 위치상 가까운 장소를 같은 날짜에 우선 배치한다. 점수 기준과 동점 처리 방식은 구현 시 설명 가능한 단순 규칙으로 문서화한다.
3. AI에 검증된 후보와 서버의 날짜별 배치를 전달해 지정 JSON 스키마로 세부 일정을 생성한다.
4. 서버가 장소 ID, 여행 기간, 방문·체류·이동 시간, 시간 중복과 운영시간·휴무 충돌을 검증한다. 검증 실패 일정은 확정하지 않는다.

기본 하루 일정 09:00~21:00, 아침 08:00~09:00·점심 12:00~14:00·저녁 18:00~20:00, 기본 체류 60~120분과 단일 이동 120분 제한은 원본을 유지한다. 첫날·마지막 날은 확인된 도착·출발 시간을 우선 반영한다. 단일 이동 120분 초과 구간은 사용자 동의 없이 같은 날 배치하지 않는다.

지도·경로 API의 예상 이동시간을 확보하면 배치 검증에 활용한다. 경로 정보가 없으면 확인 가능한 위치 정보로 기본 일정을 구성하고 최신 이동시간 확인 필요를 표시한다. 미확인 이동시간·운영시간을 검증 완료로 표시하지 않는다. 이 경우의 추정·미확인 표시와 확정 가능 범위는 일정 생성 구현 시 검증 규칙으로 구체화한다.

총 이동시간을 줄이는 방문 순서 재조정은 핵심 기능 안정화 후의 R3 선택 개선이다. 전국 도로 그래프·다익스트라 직접 구현은 제외한다. 기본 배치 점수는 서비스 계산값으로 시작하며, 이번 정리로 점수 컬럼이나 새 테이블을 추가하지 않는다. 좌표·상세 정보와 일정 항목의 이동시간·스냅샷은 기존 DB 설계를 활용한다.

## 4. 요구사항과 현재 구현의 차이

2026-09-15 보완: 조건 입력은 누락·모호한 항목만 질문하고 자연어 답변 또는 선택값을 기존 조건에 반영한 뒤 사용자가 확정한다(R1). 일정 수정은 현재 일정·조건·이번 요청에 기반한 AI 수정안을 서버에서 검증하고 사용자가 적용·저장한다(R2). 취소·실패 시 원본을 보존하며 반복 요청은 최근 적용된 일정 기준이다. 과거 대화 전체 기억·자유 상담·이전 버전 복원은 제외한다. AI 수정에도 3절의 기본 배치·검증 기준을 적용하며 이동시간 최적화를 필수로 확대하지 않는다. 두 기능 모두 구현 전이며 상세 변경은 `2026-09-15_조건보완_AI일정수정_변경내역.md`에 기록한다.

아래는 범위 조정이나 완료 선언이 아니라 남은 구현 항목이다. 현재 동작을 이유로 원본 요구사항을 낮추지 않는다.

| 항목 | 적용할 요구사항 | 현재 구현 및 남은 작업 |
| --- | --- | --- |
| 조건 분석·지역 추천의 형식 오류 | 형식 오류 시 최대 2회 자동 재요청 후 기본 추천 또는 오류 안내 | 현재 자동 재요청 없음. 지역 추천은 같은 작업에서 최초 호출 포함 총 3회까지 수동 요청 가능. 수동 요청 3회를 자동 재요청 구현 완료로 계산하지 않음 |
| 일정 검증 자기수정 | 이전 일정·구조화 오류·검증 후보를 다음 프롬프트에 전달하여 최초 1회+재생성 최대 2회, 총 3회 | 상세 일정 생성과 자기수정 모두 미구현. 라이브러리·형식 오류 재시도까지 포함해 총 호출 상한 통합 필요 |
| 외부 HTTP 호출 | WebClient 비동기 흐름, 처리 중 block() 미사용 | 현재 Java HttpClient.send() 사용. 호출 방식 변경과 시간 초과·실패 회귀 검증 필요 |
| 추천·일정 장기 작업 | 요청 스레드와 분리, 제한된 실행기, 전체 동시 실행 최대 5개, 초과 요청 QUEUED | 현재 지역 추천은 순차 1개 실행. 5개는 상한이며 findTop5 조회가 동시 5개 실행을 의미하지 않음. 처리량·응답시간 부하 검증 미수행 |
| 일정 배치·시간 검증 | 3절 순서와 시간·운영 조건 검증 | 지역 추천까지 구현. 실제 개별 장소 조회·기본 배치·시간표 생성·검증은 후속 작업 |

현재 코드의 연결 제한 5초·AI 요청 제한 25초, 큐·작업 시간 제한과 임시 보존은 서로 다른 값이다. 기존 구현 문서의 설정값은 현재 상태 설명으로 유지하고, 요구분석서의 성능 목표 달성은 별도 실행·부하 검증 후 기록한다.

## 5. 추적성과 검증 기준

3.1의 요구사항 목록에서 SFR 67개와 기타 41개(DAR 14, EIR 6, SER 6, QUR 7, TER 8), 총 108개를 확인했다. 이 적용 기준은 SFR-12-01과 QUR-06을 제외하므로 적용 대상은 106개이다. SFR-12-02~03·SFR-17-03~04는 3.1 목록에 없는 이전 식별자이며 이력용으로만 남긴다. UI 번호 21개 중 UI-17을 제외한 20개를 사용하며 이 중 UI-19~21은 R3 선택 화면이다. 이 수치는 설계 대상 수이고 구현 완료 수가 아니다.

다음 구현에서는 적합도가 높은 후보 우선 반영, 가까운 장소의 날짜별 배치, 운영시간·시간 중복·단일 이동 제한, 경로 정보 누락 안내, AI 호출 총량, 타인 작업 접근 차단을 검증한다. 새 정책이나 데이터 설계가 필요하면 이 적용 기준·DB 정의서·화면 추적표·진행 기록을 함께 갱신한다.
