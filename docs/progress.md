- 여행 조건 직접 입력·DB 키워드 선택·GPT 자연어 분석 → 조건 보완/확정 → 지역 후보 조회 → GPT 추천 순위/이유 검증·결과 저장 구현.

- 선택 지역의 장소 조회와 카카오 장소 검색, 이동시간 기반 시간대별 일정 초안까지 구현했다. 일정 초안은 `ai_jobs`에 임시 작업 결과로 저장되며 만료 시각이 있다. 회원은 날짜가 확정된 초안을 내 일정(`itineraries`·`itinerary_items`)으로 저장하고 목록·상세 조회, 이름 수정, 삭제를 할 수 있다.
- 주요 제한: 목록 표시는 관광지 16·음식점 8·숙소 5곳, 카카오 1회 검색 등록은 관광지 8·음식점 5·숙소 3곳, 카카오 후보는 조회 후 24시간만 사용한다. 일정에 쓰는 관광지는 여행 일수 × 2곳, 최대 8곳을 후보에서 선택하며 하루에 몇 곳을 배치할지는 이동시간 계산 결과에 따른다. 하루 08:00~21:00 중 4시간 이상·체류 30~180분을 입력받는다. 관광지는 근거리 우선으로 묶고 식사는 직전 관광지 기준, 숙소는 첫 후보를 사용하므로 최단 경로나 취향·예산 최적 선택이 아니다.
- 일정의 시각·장소·순서 배치는 서버 규칙과 카카오 이동시간 기반이며 GPT를 사용하지 않는다. GPT는 완성된 초안에 준비 안내만 덧붙인다. AI가 일정을 직접 생성하거나 재배치하지는 않는다.

1. 작업 시작 시 Git 상태와 최신 원격 커밋을 확인한다. Claude와 Codex는 같은 기준 커밋을 사용하며 동일 폴더를 동시에 수정하지 않는다.
2. 운영정보 기본 연결을 완료했다. 사용자 흐름은 장소 목록 → 관광공사 운영정보 확인 → 새 일정 초안 생성이다. 다음 확인은 실제 브라우저 전체 흐름·음식점/숙소 응답 표본이며, 해석 불가 예외는 확인 필요로 유지한다. 이후 AI 일정 보조의 요구사항과 현재 배치 기능 차이를 대조한다.
3. AI 일정 보조의 첫 단계(준비 안내·자기수정 제한)를 연결했다. 남은 AI 범위는 SFR-04-06 조건 충족 결과 표시와 R2인 SFR-04-07 장소 고정·부분 재추천이다. 내 일정 저장·조회·이름 수정·삭제와 즐겨찾기 등록·조회·삭제는 구현했다. 다음은 008·009 SQL 적용 후 실제 브라우저 흐름 확인 → 관리자 회원 관리 순으로 요구사항 범위 안에서 진행한다.
4. 요구분석서 3.1과 DB·화면 추적표는 관련 기능 구현 시 해당 부분을 대조한다. 전체 설계 일치 완료로 간주하지 않는다.
